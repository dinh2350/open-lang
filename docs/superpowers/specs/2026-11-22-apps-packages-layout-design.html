Apps and packages layout

Summary

Move agent, backend and frontend into apps/, and shared into packages/. e2e stays at the repository root. Nothing else changes: package names (@open-lang/*) and behavior stay the same. The reason is that more apps are expected, and moving now, before there is any CI or Dockerfile, is cheapest. The one thing to watch is the hard-coded paths in the root tooling (Vitest, ESLint, Sonar, the lcov script, each package's tsconfig.json): a missed one shows up as a failing pnpm check, pnpm sonar or pnpm test:e2e, so all three must pass afterwards.

The design

Intent and why

The repository will gain more apps. Putting deployable apps and libraries in separate folders now gives new apps an obvious place, and costs less than moving later, once CI and Dockerfiles point at the paths.

Goals

  • agent, backend, frontend live under apps/; shared under packages/; e2e unchanged.
  • Every root command works as before: pnpm dev, pnpm check, pnpm test, pnpm sonar, pnpm test:e2e, pnpm db:migrate, pnpm db:seed.
  • Docs and examples show the new paths (README.md, agent/AGENTS.md, and any other mention found).

Non-goals

  • Changing code inside any package.
  • Renaming packages or changing imports.
  • Restructuring the inside of backend, frontend or agent. That is a separate topic, not looked at yet.
  • Adding Turborepo or Nx, or splitting shared.

Anti-goals

  • A move that passes pnpm check but silently drops a package from coverage, lint or the Sonar scan because a glob no longer matches it.
  • Any lowered threshold, exclusion or suppression to get the gates passing (see CLAUDE.md).

Constraints

  • Before the work is done, pnpm check and pnpm sonar must pass, and so must pnpm test:e2e, since the change touches how the Agent and Conversation flow are started (CLAUDE.md).
  • Specs, plans and evidence go in docs/superpowers/.

Approaches

Approach Trades off Chosen
A. Keep the flat layout Free now, and fine at this size. Moving later costs more once CI and Dockerfiles exist. No
B. apps/ + packages/ now, moves only About a dozen config and doc edits, and all gates re-run. Clear place for new apps. Yes: you chose it, since more apps are expected.
C. B plus Turborepo and a split shared Pays off with slow builds or several teams. Neither is true yet. No

How it gets made

  • pnpm-workspace.yaml packages become apps/*, packages/*, e2e.
  • The four tsconfig.json files of the moved packages extend ../../tsconfig.base.json; e2e keeps ../.
  • Root vitest.config.ts: the project and coverage globs cover apps/* and packages/*.
  • eslint.config.ts: the backend/** and frontend/** globs get the apps/ prefix.
  • sonar-project.properties: sources, tests and lcov paths get the new prefixes. The e2e lines stay.
  • scripts/split-lcov-by-package.ts: finds each package under its new directory; reports still land in <package>/coverage/lcov.info.
  • README.md, agent/AGENTS.md (and the moved CLAUDE.md, if it names paths) show the new paths.
  • My call: the order is workspace file and tsconfigs first, then the root tooling, then docs, and the gates run last.

How it will be verified

  • You run pnpm install then pnpm check: it passes, and the test count is the same as before the move.
  • pnpm sonar passes, and its report still covers all four source packages and the e2e tests, with lcov for each of the four.
  • pnpm test:e2e passes: the stack starts, you register and talk to the Agent as before.
  • pnpm dev starts the backend, frontend and agent.
  • A search of the repository (excluding node_modules, lockfile and docs/superpowers history) finds no remaining reference to backend/, frontend/, agent/ or shared/ at the old root positions.

No new tests are written, because behavior does not change. The existing unit, integration and end-to-end suites are the proof: they all run through the three commands above, and the repository search covers what they cannot see (docs and stale paths).
