Astryx UI

Summary

Replace the whole look of apps/frontend (sign in, register, Conversation, admin Users) with Meta's Astryx design system, using its stone theme in both light and dark. The goal is a nicer-looking app for office workers learning English. Tailwind, shadcn, Radix and class-variance-authority are removed; Astryx is the only UI layer. Pages keep their text, behavior and flows. The Agent's voice bars need new plain CSS because they are styled with Tailwind today. The thing to watch: Astryx is beta (0.7.17), so versions are pinned exactly, and we must prove early that its components work in the project's jsdom tests.

For your review

Confirmed

  • Astryx drops into a Vite app with a few CSS imports and a theme wrapper; no build plugin (Astryx setup for Vite).
  • The stone theme has light and dark values, and the theme wrapper takes a mode of system, light or dark (stone has dark values, the mode setting).
  • Astryx is in beta and the current version of core and all seven themes is 0.7.17 (beta and version).
  • Astryx has a component for each role these pages use: text input, table, select, banner, button, link, stack, card, layout (component list).
  • Two of them do not behave like the native elements they replace. Astryx's Selector is a custom combobox button, not a native <select>, and its Table types show no caption or row-header support. Tests that use selectOptions, rowheader or the table caption are affected (component list).
  • The Agent's voice bars are styled with Tailwind classes, so they need new CSS once Tailwind goes (voice bars styling).
  • The frontend tests and the e2e tests find things by role or label, not by CSS class (how tests find elements).
  • Astryx's init command writes its guide into AGENTS.md / CLAUDE.md, and this repo's CLAUDE.md is its checked-in instructions (Astryx init).

My call

  • Pin @astryxdesign/core, the stone theme and the CLI to exactly 0.7.17, because the project is beta and its README tells exact-pinned projects to match versions (beta and version).
  • The mode toggle shows on every page, including sign-in and register, as a small control in the top-right corner (where the signed-in links already sit). Today those two pages have no header, so they get this one control. A signed-out person on a dark device must be able to change the mode.
  • The existing tests are the contract for behavior, not for how they poke the page. The plan may rewrite how a test interacts (for example, opening Astryx's Selector and clicking an option instead of selectOptions) and may adjust a query when Astryx adds a second live region. It may not weaken or delete an assertion. The e2e specs should pass as they are; change one only if Astryx forces it, and keep the change minimal.
  • Where an Astryx component cannot keep something the app does today (the Users table's row headers and caption, the role select's "You can't change your own Role." description), use the closest option in this order: another Astryx component, then a swizzled copy of that component, then a native element styled with Astryx tokens. Each such exception is listed in the plan so you can see it. This is the one place "Astryx only" bends, and only to keep accessibility.
  • The mode toggle is a two-state switch (light or dark). First visit follows the device setting; after the person toggles, their choice is saved in the browser and wins. Trade-off: once chosen, there is no way back to "follow the device" short of clearing site data. Easy to add a third state later.
  • The saved choice lives in localStorage, read and written inside try/catch so the page still works when storage is blocked.
  • Do not run astryx init against the root CLAUDE.md or AGENTS.md. If the Astryx guide is wanted for agents, put it in its own file and link it (Astryx init, project rules).
  • Keep the app's visible text and heading names exactly as they are, so existing tests and e2e queries keep working (how tests find elements).

You decided

  • Use Astryx for the whole UI, replacing everything.
  • Why: "UI đẹp hơn" (a nicer UI).
  • Astryx only: remove Tailwind and shadcn rather than keep them next to Astryx.
  • Theme: stone, because the app is an English learning site for office workers.
  • Both light and dark modes.

The design

Intent and why

Open Lang is an English-learning site for people who work in offices. They talk to an AI tutor by voice. The current UI works but looks plain. The owner wants it to look better and chose Meta's Astryx design system, with its calm stone theme, in light and dark, across the entire frontend.

Goals

  • Every page uses Astryx components and the stone theme.
  • Light and dark both look finished on every page, including error messages, the admin table and the Agent's voice bars.
  • Nothing a person could do before stops working: sign in, register, sign out, start and end a Conversation, mute the microphone, and all admin actions.
  • Accessibility does not get worse: roles, labels, keyboard use and live-region announcements stay.

Non-goals

  • New features, new pages, or changed flows.
  • Changing any visible wording or translating the UI.
  • Other Astryx themes, a theme picker, or a custom brand theme.
  • Changes to the backend, the Agent, or packages/shared.

Anti-goals

  • A UI that looks fine in light but has unreadable text, invisible borders or a broken visualizer in dark.
  • Two styling systems left running side by side, or leftover shadcn and Tailwind code that nobody uses.
  • Passing the quality gates by weakening them (no suppressions, no lowered thresholds).

Constraints

  • Astryx is beta. Pin exact versions and keep the upgrade path simple.
  • The project's rules apply: pnpm check and pnpm sonar must pass, and because this touches the Conversation flow and auth, so must pnpm test:e2e (project rules).
  • React 19 is already in use, which Astryx requires (Astryx setup for Vite).
  • LiveKit's React components stay; only their styling changes.
  • Self-hosted fonts: the stone theme's font files must load from the app, not from a third-party site, if the package ships them. See "Left to the builder".

Approaches

Approach Trades off Chosen
Astryx only; remove Tailwind, shadcn, Radix, cva One consistent look and less to maintain. Every existing Tailwind class gets rewritten. Yes, you chose it.
Astryx plus Tailwind kept, bridged by Astryx's token file Less rewriting. Two style systems, and a wrong CSS layer order silently breaks the cascade. No: you asked to replace everything.
Copy Astryx component source into the repo (swizzle) Full control of the code. We own upgrades and maintenance. No as the main route. Possible for a single component that cannot be styled enough.

How it gets made

  • Use Astryx's pre-built CSS and typed components with the stone theme, wrapped in Astryx's theme provider at the app root. No Astryx build plugin.
  • Map today's pieces to Astryx: Button, text inputs with labels, Table, Selector for the role select, Banner or Text for errors and status, Link or the router's links styled by Astryx, TopNav or Stack for the header, Card/Layout for page structure. Exact choices are the builder's.
  • Voice bars: keep LiveKit's visualizer, style it with plain CSS in voice-bars.css using Astryx color tokens so it follows light and dark.
  • Mode: the theme provider's mode comes from a small piece of state (device default, then the saved choice), toggled from the header (my call).
  • Remove Tailwind, shadcn, Radix and related packages and files once nothing imports them, and confirm with a search that none remain.

How it will be verified

  • Open the sign-in page: a stone-themed form appears. Flip the toggle to dark: everything switches. Reload: dark is still on.
  • In a fresh browser profile set to dark on the device, the first visit is dark; set to light, it is light.
  • Register, sign in and sign out work with the same messages as before, including the error shown when sign-in fails.
  • Start a Conversation: the status line still reads "The Agent is listening.", the voice bars move and are visible in both modes, the microphone toggle and End work.
  • As an admin, the Users table shows every user, and locking, unlocking, changing a role and setting a password work as before, readable in both modes.
  • Everything above is reachable by keyboard alone, with the same accessible names.

All three levels apply. Unit: the mode logic (device default, saved choice wins, toggle flips and saves, blocked storage does not crash). Integration: the existing Testing-Library page specs, which run each page against a mocked backend, must keep passing. Their interactions and queries may change where Astryx widgets differ (see "My call"), but no assertion is weakened. End to end: the existing Playwright specs pass as they are, plus one new spec that toggles dark on the sign-in page and checks it survives a reload. Because the pass criteria come from this document, tests for the new mode behavior are written from it, not from the finished code.

Left to the builder

  • Which exact Astryx component fills each role, and the page layouts, as long as wording, roles and flows are unchanged.
  • Whether the saved mode needs a tiny script in index.html to avoid a flash of the wrong mode before the app loads. Astryx documents the flash for server-rendered apps (the mode setting); this app is a Vite single-page app.
  • Whether the stone package ships its font files. In my check, the fonts.css path from Astryx's README returned 404 on the CDN for all seven themes, which may only mean the CDN path differs. Check the installed package; if there are no fonts, use the theme's fallback stack.
  • First task of the plan: prove one Astryx component renders and is queryable in this project's jsdom test setup. If a component needs test setup (for example matchMedia), add it there. If Astryx cannot run in jsdom at all, stop and tell the owner before continuing; I have not verified this.
  • The toggle's look and its exact accessible name.
