Đưa backend về đúng khuyến nghị NestJS

Tóm tắt

Refactor backend/ theo bốn mục: (1) module users sở hữu bảng User, thay vì ba nơi cùng gọi prisma.user; (2) đọc biến môi trường một chỗ bằng @nestjs/config theo docs; (3) bỏ đường dẫn /api/auth viết cứng; (4) tách file trong auth/, bỏ @Global() của Prisma, dời Throttler lên AppModule. API và hành vi không đổi, chỉ có câu báo lỗi khi thiếu biến môi trường đổi sang định dạng của @nestjs/config. Điểm cần chú ý nhất: để auth và users không phụ thuộc vòng, mình tách RefreshTokenService sang module riêng refresh-tokens/.

Để bạn xem lại

Confirmed

  • Có 10 chỗ gọi prisma.user/transaction.user ở 4 file: auth.service, authentication.guard, users.service, first-admin (nơi truy cập bảng User).
  • Có 5 chỗ đọc process.env: main.ts, seed.ts, PrismaService, AuthModule, LiveKitModule (nơi đọc biến môi trường).
  • @nestjs/config 12.1.1 tương thích Nest 12 (phiên bản @nestjs/config), và nhận schema zod qua validationSchema (docs cấu hình).
  • /api/auth bị viết cứng ở refresh-cookie.ts trong khi prefix api đặt ở configure-app.ts (đường dẫn viết cứng).
  • UsersService đang dùng RefreshTokenService của auth, nên nếu AuthService gọi lại UsersService sẽ thành vòng phụ thuộc (vòng phụ thuộc).
  • Docs nói "Making everything global is not a good design decision" (docs về module global).

My call

  • Cần bạn kiểm tra kỹ nhất: tách RefreshTokenService ra module refresh-tokens/ (chỉ phụ thuộc Prisma) để đồ thị module không có vòng. Dễ đổi lại bằng git vì chỉ là di chuyển file.
  • Dùng một schema zod chung cho cả backend và ConfigService có kiểu, thay vì registerAs theo từng nhóm. Lý do: ít file hơn và docs cũng ghi validationSchema là cách "recommended for new projects" (docs cấu hình).
  • ConfigModule đặt ignoreEnvFile: true, vì node --env-file-if-exists=.env trong script dev và start đã nạp file .env.
  • Lệnh seed dùng một SeedModule nhỏ (ConfigModule với schema riêng: DATABASE_URL và biến SEED_*) và NestFactory.createApplicationContext, để seed không đòi thêm JWT_SECRET hay biến LiveKit như hiện nay.
  • Giữ nguyên health, @AdminOnly() và guard tự viết (xem Non-goals).

Thiết kế

Ý định và lý do

Bạn thấy code backend "rất loạn" và muốn biết NestJS có khuyên làm vậy không. Review cho thấy phần lớn đã đúng khuyến nghị, nhưng có bốn chỗ lệch làm code khó đọc. Mục tiêu là sửa bốn chỗ đó mà không đổi hành vi.

Mục tiêu

  • Chỉ UsersService đọc/ghi bảng User. Hàm toUser và toUserDetails nằm trong users/.
  • Mọi biến môi trường của backend được validate một lần lúc khởi động bằng @nestjs/config và đọc qua ConfigService. Không còn process.env trong src/, trừ chỗ khai báo schema.
  • Prefix api và path auth khai báo một lần trong src/routes.ts. Cookie refresh, controller và configureApp cùng dùng.
  • auth/ được tách thành guards/, decorators/, exceptions/. AuthenticatedRequest chỉ định nghĩa một lần. Kiểu ValidRegisterRequest/ValidSignInRequest ra khỏi service.
  • PrismaModule không còn @Global(); các module cần thì import. ThrottlerModule.forRoot nằm trong AppModule. Test helper chung gom vào test/support/.

Non-goals

  • Không đổi API, mã trạng thái, thông điệp lỗi của route, schema DB hay migration.
  • Không đụng agent/, frontend/, và không sửa shared/ (parseEnv vẫn còn cho nơi khác dùng).
  • Không thêm @nestjs/terminus, @nestjs/passport hay @Roles().

Anti-goals

  • Sửa test cho khớp code mới ở chỗ hành vi thật bị đổi (ví dụ nới validate để test xanh).
  • Backend khởi động được khi thiếu hoặc sai JWT_SECRET, DATABASE_URL, biến LiveKit.
  • Dùng NOSONAR, @ts-ignore, hạ ngưỡng lint/Sonar (cấm trong CLAUDE.md).

Constraints

  • Phụ thuộc giữa các module không được có vòng: Nest báo lỗi khi khởi động nếu có, và forwardRef bị docs không khuyến khích.
  • Trước khi xong phải qua pnpm check và pnpm sonar. Vì chạm vào auth nên phải chạy thêm pnpm test:e2e (CLAUDE.md).
  • Test backend cần Docker (Testcontainers).

Hướng phụ thuộc sau khi sửa

PrismaModule
   ├── UsersModule          (UsersService: find/create + thao tác của Admin)
   └── RefreshTokensModule  (RefreshTokenService)
          ▲
AuthModule ──imports──► UsersModule, RefreshTokensModule
   │  (APP_GUARD, JwtModule, AuthController)
   └── decorators/guards được users, livekit, health import theo file
UsersModule ──imports──► RefreshTokensModule   (không import AuthModule)
AppModule: ConfigModule (global), ThrottlerModule, các module trên

Cách làm

  • Mục 1. UsersService thêm findById, findByEmail, create. AuthService và AuthenticationGuard gọi qua đó; việc đổi lỗi unique (P2002) thành 409 vẫn nằm ở AuthService. toUser chuyển thành users/user.mapper.ts; auth/users.ts bị xóa. first-admin.ts dùng UsersService khi seed chạy trong ngữ cảnh Nest. (my call)
  • Mục 2. Thêm @nestjs/config. Một schema ở src/config/env.schema.ts ghép liveKitEnvSchema (từ shared) với PORT (mặc định 3000), DATABASE_URL, JWT_SECRET. PrismaService, AuthModule (JwtModule.registerAsync), RoomTokenService và main.ts đọc qua ConfigService. Bỏ LIVEKIT_CONFIG và loadLiveKitConfig. Câu báo lỗi khi thiếu hoặc sai biến đổi sang định dạng của @nestjs/config.
  • Mục 3. src/routes.ts xuất API_PREFIX và AUTH_PATH. Path của cookie tính từ hai hằng số này. (my call)
  • Mục 4. Như mục Mục tiêu. Tên file cụ thể (ví dụ public.decorator.ts) theo quy ước docs.
  • Làm tuần tự: mục 3, mục 4, mục 1, mục 2. Mỗi bước chạy test backend rồi mới sang bước sau. (my call)

Cách kiểm chứng

  • Toàn bộ spec hiện có của backend (đăng ký, đăng nhập, refresh, đăng xuất, khóa User, đổi quyền, đặt mật khẩu, token phòng, giới hạn tốc độ) vẫn qua, mà không phải sửa nội dung kiểm tra hành vi.
  • Thiếu JWT_SECRET, DATABASE_URL hoặc một biến LiveKit thì backend từ chối khởi động và lỗi nêu đúng tên biến. LIVEKIT_URL không phải WebSocket, hoặc JWT_SECRET ngắn hơn 32 ký tự, vẫn bị từ chối.
  • Cookie refresh vẫn có Path=/api/auth; đổi hằng số thì cả route và cookie đổi theo.
  • pnpm db:seed trên database trống tạo Admin chỉ với DATABASE_URL và biến SEED_*, không cần JWT_SECRET.
  • Trình duyệt: đăng nhập, mở phòng, đăng xuất chạy như trước (e2e Playwright).

Integration: các spec backend hiện có chạy với Postgres thật; test khởi động và test seed được viết lại theo định dạng lỗi mới. Unit: thêm test nhỏ cho schema môi trường (hợp lệ, thiếu biến, sai định dạng, mặc định của PORT). E2E: chạy pnpm test:e2e vì thay đổi chạm vào auth.

Rủi ro cần xác minh khi bắt đầu làm

  • Docs không nói ConfigModule.forRoot() validate lúc nào. Nếu nó chạy ngay khi file module được import, thì vi.stubEnv trong test/test-app.ts chạy quá muộn. Khi đó test sẽ nạp AppModule bằng import() động sau khi đặt biến môi trường. Bước đầu tiên của kế hoạch là kiểm tra điều này.

Để người thực hiện quyết

  • Tên file và thư mục con cụ thể trong auth/, miễn theo quy ước docs.
  • Thứ tự chia commit, miễn mỗi commit qua pnpm check.
